# Walk-forward evidence improvement plan

Learning owns strategy outcome attribution and replay. Insights provides market inputs and fee-aware markouts; it does not infer strategy performance from raw signals. Keep the worker boundaries and change the live gate only after the new evidence pipeline is reproducible and offline validation is complete.

This plan targets Scout strategy/profile evidence used by the Strategy live-entry gate. Learning’s per-parameter `walk_forward_threshold` tuner is a separate path; do not merge it into this evaluator until its candidate history and estimand are covered by the same replay design.

## Milestone 1: Make the historical data complete and auditable

1. [x] Inventory the Scout SQLite collections and Learning outcome store. Verify which fields are present for signal/evaluation time, costs, strategy/profile parameters, regime, outcome group, baseline, and candidate selection.
2. [x] Make analytical replay read all durable outcomes in timestamp order. The runtime replay index hydrates only the latest 4,096 Scout outcomes; SQLite is the durable source and eviction only removes the runtime copy. Report missing or truncated history as coverage, never as a complete sample.
3. [x] Audit `scout_plan_results`: it stores selected groups/audits and is cached separately, but may not record every candidate tried or the selection process. Add a durable append-only search record containing search ID, as-of cutoff, all candidates and parameter sets considered, baseline, selection metric, selected candidate, and evaluation window.
4. [x] Give outcomes a stable identity and eligibility rules: completed before the evaluation origin, fee-aware, exact profile and symbol, explicit regime, and grouped when they share an opportunity/portfolio decision. Keep missing marks/costs and any broader-profile fallback explicit.

**Deliverable:** a versioned, point-in-time dataset contract plus durable outcome/search readers with coverage diagnostics.

**Inventory findings (2026-11-19):** Scout outcomes are durably stored in `scout_records.outcomes`; the replay reader orders them by `evaluated_timestamp_ms` and record key, bypasses the 4,096-row runtime cache, and reports malformed/missing-row coverage. Outcome payloads include decision identity, signal/evaluation timestamps, symbol/strategy/profile context, strategy parameters, fee rate and net result, optional regime, sample group, and comparison/baseline role and IDs. Learning's outcome details are persisted inside variant payloads, but its working history is bounded to seven days and 512 outcomes per variant (plus global memory limits), so it is not a complete historical replay source. The outcome fields still lack an explicit cost breakdown. The legacy `scout_plan_results` collection is not a complete search ledger; step 3 adds a separate append-only `scout_search_ledger` collection, which is the source for full search history.

**Replay-reader verification (2026-11-19):** `GET /replay/outcomes` reads directly from SQLite, orders by evaluation timestamp and record key, returns the full durable collection, and reports total, returned, and malformed row counts plus timestamp bounds. A persistence test verifies that outcomes outside the 4,096-row hydration cache remain in SQLite and are visible to durable history reads. Its `complete` flag describes successful reading of the current database; it cannot establish that historical records were never lost before being written.

**Search-ledger verification (2026-11-19):** Each plan request is persisted by request ID as an immutable SQLite record. It captures the as-of/outcome cutoff, every original input plus each expanded candidate and parameter map, baseline audits (or an explicit `not_provided` status), selected candidates, effective-sample shortfall scores and ranks, the target of 10, and the rotation tie-break order. The evaluation window is recorded as starting at the plan timestamp and ending when each selected candidate's configured outcome scenario completes; the current planner has no fixed end horizon. Runtime cache eviction does not delete ledger rows. Focused persistence, cache-retention, candidate-priority, worker-route, and cross-worker replay aggregation tests pass. The metric records evidence-acquisition priority; it is not a return-based candidate-selection objective.

**Eligibility-contract verification (2026-11-19):** Replay version 2 exposes the SQLite record key as `outcome_id`, reconstructs `profile_id` from the exact profile symbol, strategy, and recorded parameters, and reports eligibility against an optional strict `origin_at_ms` cutoff. Each row marks profile-symbol fallback, canonical or missing regime, fee-rate/net-return availability, cost-breakdown availability, and the evidence-group ID/source. Coverage includes open instances and expired instances without outcomes. AutoTrader's walk-forward evidence now carries an `evidenceScope` distinguishing exact-profile evidence from symbol/strategy fallback at profile and regime scope. The contract reports cost breakdown as unavailable rather than treating the fee-rate/net-return pair as a full cost ledger. The origin must be supplied by the rolling-origin replay caller; without it, rows explicitly report `origin_not_supplied`.

**Search-reader verification (2026-11-19):** `GET /replay/searches` reads every durable `scout_search_ledger` row in as-of/request order and reports total, returned, and malformed counts. Learning routes it to every configured Scout worker, qualifies search IDs by worker strategy, and merges rows in deterministic global order. The persistence/cache and cross-worker reader tests pass.

## Milestone 2: Generate rolling-origin out-of-sample returns

1. Predeclare replay settings: expanding or rolling training window, minimum history, origin cadence, evaluation-window length, final holdout, and candidate-selection objective. Persist a config/version hash with results.
2. At each origin, select/tune using only records available before that origin. Apply the selected candidate to the next untouched interval; repeat chronologically. Use the final holdout once for confirmation.
3. Emit aligned portfolio/time-period return streams for each candidate and baseline, net of modeled fees and costs. Include flat/cash periods when the replay establishes that no position was held; do not silently convert missing outcome marks into zero returns. Preserve opportunity/group IDs, timestamps, profile, regime, fold boundaries, and missing-outcome coverage. Trade-only averages can favor candidates that trade less often and are not comparable as portfolio expectancy.
4. Keep the strict `evaluated_at < origin_at` rule. Retain the existing non-overlap treatment or purge training observations whose label windows intersect an evaluation window; set any embargo before seeing results. Do not mix symbols or portfolio legs as if independent.

Rolling-origin evaluation is the primary deployment-style estimate ([Tashman, 2000](https://doi.org/10.1016/S0169-2070(00)00065-0)).

**Deliverable:** deterministic replay output that can reproduce each fold and explain each included/excluded observation.

**Predeclared replay defaults (config version 2, 2026-11-19):** use an expanding training window with at least 30 independent UTC-day clusters and effective sample size 10; place origins every 7 days; assign the next 7 days of candidates to each evaluation fold by signal time; reserve the final 28 days as a single untouched holdout; select candidates by aligned net portfolio expectancy versus baseline, including established cash periods. Training remains strictly `evaluated_at < origin_at`; evaluation outcomes may mature after the 7-day signal window. Dependence-aware inference is predeclared as 512 stationary bootstrap replicates with a 7-day expected block length; the searched-family SPA requires 30 independent day clusters. The typed configuration has a deterministic hash; persisted fold/holdout assignments are described in the run-persistence update below.

**Replay run persistence update (2026-11-19):** each deterministic paired-return response now has a dataset hash and stable run ID. Learning persists up to 32 run summaries in its normalized SQLite state, including config version/hash, source coverage, incomplete status, fold IDs, and final-holdout assignments; `GET /scout-replay/runs` lists the retained runs. This closes replay configuration/result-assignment persistence. It does not persist return streams or make selection available; the underlying portfolio timeline and flat intervals remain absent.

**Return-stream implementation note (2026-11-19):** the Learning route `/scout-replay/paired-returns` emits matched baseline/variant outcome pairs with opportunity IDs, candidate-search linkage, modeled notional/weight, markout cost details, and UTC signal day. It deliberately returns `status: incomplete`, emits no cash-period zeros, and disables selection because the current durable outcome/search collections do not establish the full position/candidate timeline needed to prove flat periods. It now emits deterministic expanding-window fold and final-holdout assignments with the config hash, strict training cutoff audit, and each fold's pair IDs. These are assignment diagnostics only: results are not durably persisted, candidates are not selected, and final-holdout returns are not used to confirm a selected candidate. A complete portfolio/cash timeline remains required before selection or deployment estimates are available.

**Milestone 2 implementation status (2026-11-19):** step 1's settings are defined and version-hashed; fold responses carry that hash. Steps 2–4 remain incomplete because the paired outcome/search data does not identify every candidate opportunity or establish held-versus-flat portfolio intervals. No missing interval is converted to a zero, and no candidate selection is run from these partial assignments.

**Replay audit hardening (2026-11-19):** paired rows now require explicit profile identities on both arms and exactly one baseline match for the comparison, opportunity context, and exit scenario. Ambiguous matches are excluded and reported in coverage instead of multiplying candidate observations. The replay contract exposes each outcome's signal-to-completion label window and purges training rows whose label end is missing or overlaps an origin. Markout cost breakdowns are explicitly marked partial and cannot satisfy complete-cost coverage. The append-only search ledger now records reasons for filtered, cooled-down, already-active, ineligible, and batch-limited candidates. This still does not supply the full candidate/opportunity portfolio timeline, held-versus-flat intervals, or exact search-to-outcome identity needed to enable selection.

## Milestone 3: Add dependence-aware inference

1. Calculate selected-candidate net expectancy against the baseline from the out-of-sample stream. Keep positive-return rate and non-overlap count as diagnostics.
2. Calculate a one-sided lower confidence bound using a deterministic stationary bootstrap over chronological UTC-day clusters (512 replicates, seven-day expected blocks). Report the effective number of independent day clusters; multiple outcomes on one day count as one dependent cluster.
3. Report fold/window coverage, drawdown and downside summaries alongside the interval. Flag regime instability and sparse regimes; do not let one aggregate interval hide them.
4. After the full search ledger is available, run Hansen’s SPA test on the searched candidate family versus baseline using a dependence-aware bootstrap. Preserve the full tried set, including failed candidates. SPA is a family-level test for superior performance, not a guarantee that a selected candidate will remain profitable ([Hansen, 2005](https://citeseerx.ist.psu.edu/document?doi=3fc027710d7a2bab33abe3ee33e93c765190394f&repid=rep1&type=pdf)).
5. Add Sharpe/DSR or PBO/CSCV only if a separate Sharpe-selection or search-fragility question warrants it; neither replaces forward evaluation ([DSR](https://davidhbailey.com/dhbpapers/deflated-sharpe.pdf), [PBO/CSCV](https://escholarship.org/uc/item/4w1110bb)).

The stationary bootstrap supports inference for weakly dependent stationary series; regime changes must be surfaced rather than assumed away ([Politis & Romano, 1994](https://users.ssc.wisc.edu/~bhansen/718/Politis%20Romano.pdf)).

**Deliverable:** a reproducible evidence summary with expectancy interval, SPA result when eligible, diagnostics, and explicit evidence status/coverage.

**Current implementation audit (2026-11-19):** Learning has a deterministic stationary bootstrap over UTC-day clusters for its existing walk-forward outcome summaries. A selected-stream one-sided expectancy interval and Hansen SPA implementation now accept only aligned, complete daily portfolio rows, require explicit source and cash-period coverage, and have deterministic synthetic tests. Milestone 3 is not complete: these estimators cannot run on the current trade-only paired rows, and no actual selected-stream expectancy/SPA result or fold/regime coverage report is available.

**Inference engine update (2026-11-19):** the replay config is now version 2 and hashes the stationary bootstrap method, 512 replicates, seven-day expected block length, and 30-day minimum for SPA. Learning implements a one-sided selected-stream expectancy interval and Hansen's studentized SPA test with sample-dependent null centering and stationary day blocks. Synthetic deterministic tests cover confidence bounds, family p-values, alignment, missing cash periods, and gaps. Paired replay emits and persists `unavailable_until_complete_portfolio_timeline`; none of these estimators is run on trade-only pairs or used for candidate selection.

## Milestone 4: Validate the replacement and cut over

1. Version the evidence contract across Learning’s decision snapshot, AutoTrader profile payload, and Strategy gate. Include evidence status, point-in-time cutoff, profile/regime, sample and effective counts, window coverage, estimate/interval, and search/SPA metadata.
2. Validate replay offline across symbols, regimes, windows, sparse-data cases, and missing-data cases. Confirm determinism and strict time cutoffs; replay saved inputs to verify the new estimator and its decisions.
3. Replace the average-return/positive-rate gate directly. When evidence is mature and fresh, require the 95% lower confidence bound on net expectancy to exceed 0%. New or sparse profiles continue through the existing capped exploration path; learned-paused profiles report missing, stale, or inadequate evidence as the reason they remain paused.
4. Set acceptance thresholds before evaluating the final holdout. If the replacement fails validation, revise it before cutover; do not retain the old rule as a fallback or run both gates against live decisions. Preserve immutable entry-time evidence for attribution and audit.

**Deliverable:** offline validation report and a directly replacing expectancy-based entry gate.

**Current implementation audit (2026-11-19):** Strategy's live gate currently requires the one-sided expectancy lower bound to clear zero for mature evidence, with sparse profiles following exploration behavior. The cutover is not accepted as complete: the rolling-origin portfolio replay and untouched holdout confirmation are unavailable, and no offline validation report has checked determinism, cutoff behavior, sparse/missing cases, regimes, or saved-input decisions. Do not treat the current gate change as validated for deployment.

**Evidence-contract update (2026-11-19):** `StrategyWalkForwardEvidence` now carries contract version, estimator identity, history/cost/search coverage, point-in-time cutoff, OOS fold count, SPA p-value, and final-holdout validation status through Learning snapshots and AutoTrader/Strategy profiles. Existing evidence is identified as completed-outcome cluster bootstrap with partial/unknown source coverage and `not_validated`; it is not relabeled as rolling-origin evidence. Candidate diagnostics display this contract. The Strategy gate continues to enforce its existing lower-bound rule while validation is pending. Offline saved-input validation and any evidence-gated cutover remain outstanding until a complete portfolio timeline is available.

## Milestone 5: Make every entry blocker obvious

1. Publish a typed latest-cycle diagnostic with outcome, cycle/time identity, signal/candidate/selection/order counts, primary gate ID, blocker detail, and confirmed fill count. Keep reason text for reading; the UI must not infer the cycle outcome from it.
2. Carry a decision/cycle ID through signal eligibility, strategy evaluation, walk-forward gating, candidate selection, position/risk checks, execution checks, and order submission. Record all applicable failures, not only the last error or first rejection.
3. Publish an entry funnel per cycle: signals received, fresh/directional candidates, candidates passing strategy and evidence checks, candidates passing portfolio/risk/execution checks, selected orders, and submitted orders. Distinguish “no eligible signal” from “candidate rejected” and “order failed after selection.”
4. Expose the current cycle’s primary blocker and counts by gate, symbol, and strategy in the AutoTrader UI/API, with drill-down to each candidate’s full reasons and the concrete values that failed. Mark gates that are informational or indeterminate so they are not confused with blockers.
5. Keep a bounded recent history and timestamp so an empty or stale diagnostics panel is itself visible. Avoid a dashboard that reports zero trades without a corresponding reason or an explicit diagnostics-unavailable state.

**Deliverable:** an end-to-end “Why no entry?” view that identifies the dominant blocker and lets the user inspect every candidate and gate decision.

**Current implementation audit (2026-11-19):** the AutoTrader API/UI exposes a typed latest-cycle outcome, counts, primary blocker, and candidate-level decision detail. Milestone 5 remains open pending per-cycle gate-count reconciliation through the full entry funnel, structured observed-versus-required values for all applicable blockers, and a bounded timestamped history with an explicit diagnostics-unavailable state.

**Diagnostics instrumentation update (2026-11-19):** AutoTrader returns the latest 100 typed cycle diagnostics and preserves them across daily counter and submitted-trade resets. Strategy worker decisions and skips retain profile/event identity, same-event reports from different profiles are kept separately, and the UI shows per-profile reasons with freshness. Entry diagnostics carry a unique cycle ID, candidate decision IDs, worker event IDs, per-cycle gate counts by symbol/strategy, funnel counts for fresh, stale, directional, position-blocked, strategy-rejected, and evidence-present candidates, plus candidate observations, thresholds, checks, reasons, and stage outcomes. Milestone 5 remains open: later portfolio/risk/execution checks still need structured observed-versus-required values, and the counts have not yet been reconciled with each execution and order transition.

## Acceptance criteria

- Replay reads complete durable history or reports exactly what is missing; the runtime 4,096-row cache is never treated as the whole history.
- Every search records the complete candidate family and selection cutoff; SPA is withheld when this history is incomplete.
- No outcome evaluated at or after an origin contributes to its training or evaluation result.
- Candidate and baseline returns are aligned, fee-aware, and resampled in time/group blocks.
- The final holdout is never used to tune. Offline replay validates the replacement; only the replacement gate runs on live decisions after cutover.
- Every cycle with no submitted trade reports whether there were no eligible candidates, which gates rejected candidates, or why a selected order failed; diagnostics include structured reasons and observed-versus-required values.
- Gate counts reconcile through the entry funnel, and the UI/API expose the current reason with freshness and candidate-level detail.
